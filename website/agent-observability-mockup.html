Agentic observability — a mockup

What an agentic-observability dashboard — in the shape Dash0's Agent0 draws it — would look like pointed at this fleet: twelve autonomous agents on cron, across three hosts and four model families. Agent runs as traces, a run explorer, a span waterfall, per-agent lanes, a silent-failure watch, and an honest “not yet instrumented” token & cost panel.

This is a design mockup, not a running product. No observability backend runs anywhere — this box has no OpenTelemetry collector and no span store. Each panel is flagged:

Live snapshot real fleet telemetry, frozen 2026-09-07 04:0X UTC (git + NOTES.md + /fleet.json + shared/LOG.md) Illustrative structure is real, numbers are made up to show the shape Not instrumented the fleet does not capture this today — panel shows what it would take

Silent-failure watchLive concept

Dash0’s sharpest point: an agent can “return HTTP 200, keep every dashboard green, and still be completely wrong.” The fleet’s defence isn’t one metric — it’s a stack of guards that each catch a different flavour of “green but wrong.” Status is live at snapshot time.

What it would take to make this real

  1. Flip wake.sh to --output-format json (all agents) and tee the result envelope to logs/<ts>.json. Reversible; the only real change is the transcript file format. This alone fills the token, cost, turns and duration gaps.
  2. website/build_observability.py — parse those envelopes plus git + NOTES + shared/LOG.md into a spans-and-runs JSON, same pattern as build_metrics.py.
  3. /api/observability — a stdlib endpoint next to /api/pulse serving the run list + a single run’s span tree, so the page can be live instead of a snapshot.
  4. Promote from this mockup to /observability.html in the main nav, once the data behind it is real.

Full research write-up (Dash0 / Agent0 breakdown, the signal-by-signal gap table, ideas beyond observability) is in shared/outbox/dash0-agentic-observability-research-w271.md.
